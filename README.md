## 它是什么

一个完全自托管的 AI 对话系统：React 单文件 PWA + Node.js 网关 + 六个微服务，全部跑在一台 VPS 上。模型层可插拔（任何 OpenAI 兼容端点或 Anthropic 原生），数据全部落在自己的服务器和设备本地。

它要解决的问题是：**一个每天都在用、要用很多年的对话系统，需要哪些基础设施？**

普通 chatbot 的答案是「更好的模型」。这个项目的答案是：模型只是其中一层。真正决定长期体验的是——

- **上下文怎么装配** —— 大部分内容逐轮不变但必须一直在，切分方式直接决定成本
- **记忆怎么筛选** —— 只增不减的记忆库三个月后就会失去判断力
- **工具怎么调用** —— 上游中转会静默丢弃 `function_call`，得有 B 方案
- **状态怎么持久** —— 情绪、进度、待办这些跨会话的东西放在哪
- **坏了怎么恢复** —— 删掉 PWA 等于清空本地存储

## 一个具体的例子

三天前你发过一张照片。当时模型除了正常回复，还顺手写了一段隐藏的场景描述，持久化到那条消息上。

今天你在**另一个会话窗口**说「那天那张照片」——

模型知道你指的是哪张。因为上下文的五层里只有「近期消息」是窗口内的，图片描述跟着消息对象走；同时记忆层浮上来的话题池里，那张照片相关的条目还没到期。

这件事需要三个机制同时成立：[图片描述持久化](docs/03-chat.md)、[跨窗口的上下文分层](docs/02-context.md)、[有寿命的记忆筛选](docs/05-memory.md)。任何一个缺席，它就变成一句「抱歉，我不太清楚你指的是哪张照片」。

## 诚实交代

- **单用户设计。** JSON 文件存储、人工过手的记忆固化、单文件前端——这三个选择在多用户场景下都会立刻失效。这不是还没做，是不打算做。
- **文档写的是当前状态。** 所有数字（行数、服务数）都是实测的；每篇末尾的「代价」小节写的是真踩过的坑，不是补上去的免责声明。
- **`docs/` 只有中文。** 英文读者请看 [README.en.md](README.en.md)，那是一份完整概览而不是摘要。
