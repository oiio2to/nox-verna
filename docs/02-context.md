# 02 · 上下文装配

> 一条消息发出去之前，上下文是怎么拼起来的；换一个会话窗口为什么不会断片；以及提示词缓存怎么切才不会白付钱。

---

## 问题

伴侣类应用的上下文有一个和普通 chatbot 不同的性质：**大部分内容和当前这句话无关，但必须一直在**。

人设、世界书、今天是在一起第几天、正在一起听的歌、脉搏花园的八维数值、森林里浮上来的念头——这些每一轮都要送，因为随时可能被用到。结果是：

- 单次请求的 system 部分很容易到几万 token
- 其中 90% 逐轮不变，但只要有一个字节变了，整段缓存就作废
- 一天下来光是重复送这些内容的成本，比真正的对话内容高得多

所以上下文装配的核心问题不是「送什么」，是**怎么切分，才能让不变的部分一直命中缓存**。

---

## 分层结构

上下文由五层拼装，按「变化频率」排列：

| 层 | 内容 | 变化频率 | 跨窗口 |
|---|---|---|---|
| 人设 & 工具说明 | 角色定义、语气规范、所有工具的协议说明 | 几乎不变 | ✅ 全局 |
| 每日内容 | 日期、星期、在一起第几天、纪念日提醒 | 一天一次 | ✅ 全局 |
| 会话摘要 | 本窗口滚动摘要 + 每日记忆蒸馏 | 每轮可能变 | 摘要层全局 |
| 生活面板状态 | 正在听的歌与进度、共读批注、脉搏八维、森林话题池 | 实时 | ✅ 服务端状态 |
| 近期消息 | 当前窗口最近 N 条（含语音转写、图片场景描述） | 每轮变 | 窗口内 |

这个排序不是为了好看。它直接决定了缓存断点打在哪里。

**跨窗口不断片的效果**：吵完架开一个新窗口，第一句话模型就知道你们为什么吵、现在几点、正在一起听哪首歌的第几句。因为前四层里只有「近期消息」是窗口内的，其余全是全局或服务端状态。

---

## BP1 / BP2 / BP3 · 三段式缓存分层

这是这一章最值得说的部分。

### 为什么要切

Anthropic 的提示词缓存按**前缀**命中：从头开始逐字节比对，遇到第一个不同就往后全部失效。缓存写入还有大约 2× 的价格溢价——挂了缓存但读不回来，等于白付一次溢价。

如果把整个 system 拼成一大段，那么「今天是在一起第 31 天」这一句变了，**整段人设和工具说明的缓存全部作废**。而人设和工具说明恰恰是最大、最贵、最不该重算的部分。

### 怎么切

前端按稳定度把 system 拆成三块，用一个分隔符 `⟦BP⟧` 拼在一条 system 消息里送过来，网关切开成独立块：

```js
const sys2 = [];
for (const blk of sys)
  for (const part of String(blk.text || "").split("\u27E6BP\u27E7")) {
    const t = part.trim();
    if (t) sys2.push({ type: "text", text: t });
  }
```

| 块 | 内容 | 失效频率 |
|---|---|---|
| **BP1** | 人设、语气、全部工具协议说明 | 改了才变，通常几周 |
| **BP2** | 日期、星期、在一起第几天、纪念日提醒 | 一天一次 |
| **BP3** | 会话摘要、记忆浮现、生活面板状态 | 每轮可能变 |

每块单独挂 `cache_control`，形成**独立断点**：BP3 变了不影响 BP1 和 BP2 的命中。

API 最多允许 4 个断点。这里用掉 3 个，**第 4 个留给 messages 里的 rolling 标**——让近期消息也能滚动缓存。

### 一个不明显的收益：跨面板共享

日记、信件、共读批注、朋友圈这些旁路功能各自有专属说明，但它们**共用同一份人设底座**。

前端把内容拼成 `共用底座 ⟦BP⟧ 本面板专属说明` 送过来，网关切开之后，**所有面板的第一块逐字节一致**。于是 BP1 在所有面板之间共享同一份缓存——写日记时命中的是聊天时写入的那份。

### 什么时候不挂缓存

旁路的一次性调用（生成日记、写信、签名、共读批注、朋友圈回复）每次的 system 都不一样。这类调用**不挂缓存**：

```js
const _noCache = !!noCache;
const nbp = _noCache ? 0 : (sys2.length >= 3 ? 3 : 1);
```

理由是写进去的缓存永远读不回来——挂标只会白付 2× 写入溢价，还把命中率统计稀释掉。

块数本身就是判据：

- **≥3 块** = 主聊天（底座 / 工具 / 每日），前三块各挂一个断点
- **1–2 块** = 旁路面板调用，只挂第 1 块（共用底座）；第 2 块是本面板专属说明，挂了也读不回来

### BP2 的设计意图

BP2 单独存在的价值不在于内容多，而在于它的**变化节奏**：

有东西天天要换，但它换了只作废 BP2 往后，不动 BP1。

BP2 一天生成一次，一天之内逐字节不变。内容全自动：日期、星期、在一起第几天、纪念日提醒。想手写点什么（今天的安排、心情基调），写进 `data/bp2-daily-extra.txt` 会自动接在后面——**手写内容也只影响 BP2 这一层**。

时间统一按东八区计算，避免服务器时区抖动导致 BP2 在午夜前后反复失效。

---

## 记忆注入的时间围栏

从记忆系统浮上来的内容有一个特有的风险：**模型会把过去的事当成正在发生的事。**

三天前的一段对话摘要如果直接拼进 system，模型很可能在下一句里说「你刚才不是说……」。

解决方式是给记忆块加显式的时间围栏——注入内容前后各有一句明确的标记，说明这一段是过去的记忆，以及从哪里开始回到当前。这条规则看起来很土，但没有它，记忆注入几乎必然污染当前语境。

---

## 代价

**前端要负责切分。** 稳定度分层的判断在前端做，网关只负责切开和挂标。这意味着新增一个 system 内容时，写的人必须想清楚它属于哪一层——放错层会导致缓存频繁失效，而且不会报错，只会变贵。

**断点用满了。** 4 个断点用掉 3 个固定 + 1 个滚动，没有余量。再想加一层缓存分层就必须合并现有的。

**跨面板共享要求底座逐字节一致。** 只要有一个面板在底座里多写了一个空格，它就会独立占一份缓存。这个错误很难发现——功能完全正常，只是账单变高。为此网关侧对切出来的块做了 `trim()`，消掉最常见的一类差异。
