# 03 · 多模态对话

> 语音、图片、视频进了上下文之后会发生什么。核心问题只有一个：**多模态内容在下一轮就消失了。**

---

## 共同的问题：多模态没有记忆

发一张图片，模型这一轮能看见。下一轮上下文里剩下的是什么？

一个 URL。

模型看不见 URL 指向的内容，于是三天后你说「那天那张照片」，它完全不知道你在说什么。语音和视频同理——转写和帧只在当轮存在。

**多模态是即时的，上下文是持久的，这两者天然不匹配。** 这一章的三个机制都在解决同一件事：把即时的东西固化成持久的文本。

---

## `⟦IMGDESC⟧` · 图片连续性

模型第一次看到图片时，除了正常回复，还顺手写一段隐藏的场景描述：

```
（正文回复…）
⟦IMGDESC⟧海边黄昏，她穿蓝裙子回头笑⟦/IMGDESC⟧
```

前端把标记剥离，正文正常渲染，描述**持久化到消息对象上**。此后每一轮上下文注入时，这条消息带上一句：

```
[这条发过照片，画面：海边黄昏，她穿蓝裙子回头笑]
```

三天后再聊起那张照片，模型记得裙子是蓝的。

### 几个设计细节

**为什么让模型自己写，而不是用视觉模型批量生成描述？** 因为模型在当轮有完整的对话语境。同一张照片，在「今天去海边玩」和「翻到三年前的照片」两个语境下，值得记住的东西不一样。脱离语境的客观描述反而更差。

**为什么是隐藏的？** 让用户看到「AI 正在给我的照片写描述」会破坏体验。这个动作应该是无感的。

**描述写多长？** 提示词里要求一句话。太长会在长对话里累积成显著的 token 成本——一百张图片就是一百段描述，每轮都在送。

### 视频

同一套思路，输入换了：`ffmpeg` 均匀抽帧 + 音轨走 STT 转写。帧和转写一起送给模型，模型同样写一段 `⟦IMGDESC⟧`。之后上下文里留下的是这段描述，不是几十张帧。

---

## 语音条

### 输入方向

录音上传 → 服务端 STT 转写 → **转写文本进上下文**。

模型收到的是文本，不是音频。这是有意的：音频进上下文的成本远高于文本，而对伴侣类对话来说，语气信息用文本描述（「她声音听起来很累」）反而更容易被模型利用。

消息对象上同时保留音频文件和转写文本。界面里显示的是语音条，上下文里送的是文本。

### 波形

波形不是装饰性的随机数——它是从音频数据算出来的真实振幅包络，所以说话密集的段落波形更密，停顿处平坦。

胶囊内直接提供下载。

## 坏流自愈

流式响应会以各种奇怪的方式坏掉。遇到过的、并且做了处理的有两类：

### 正文藏在 `</thinking>` 之后

某些模型或中转在思考链处理上有问题，会把整段回复放进思考块里，或者思考块的闭合标签之后才是真正的正文。

处理：解析时不假设结构，如果 `</thinking>` 之后有非空内容，就把它当正文捞出来渲染。

### 双重编码的 SSE

中转层偶尔会把 SSE 事件再包一层 JSON 编码，于是前端拿到的是转义过的字符串而不是可解析的事件。

处理：解析失败时尝试反转义一次再解析。成功就继续，失败就把原始内容当文本吐出——**永远不静默丢弃**。

这两个处理都很土，但它们的价值在于：坏流的时候用户看到的是稍微奇怪的回复，而不是一片空白。在一个每天都在用的应用里，这个差别很大。

## 其他对话能力

| | 说明 |
|---|---|
| 语音 / 视频通话 | TTS 播放 + 背景视觉，走同一套上下文 |
| 引用回复 | 拖拽气泡引用，引用内容进上下文 |
| 消息收藏 | 收藏的消息可被记忆系统优先拾取 |
| 重新生成 | 因为工具结果是拼进当前轮的，重新生成必须重跑整轮（见 [04](04-agent.md)） |
| 思考链折叠 | 默认折叠，可展开 |
| 多会话窗口 | 窗口内消息独立，其余上下文层全局（见 [02](02-context.md)） |

## 代价

**`⟦IMGDESC⟧` 依赖模型配合。** 模型偶尔会忘记写，或者写得很敷衍。没有强制机制——加了强制反而会在不需要描述的场景产生噪音。目前的做法是在提示词里给正例和反例，接受偶尔的遗漏。

**描述累积成本。** 长对话里图片描述会持续占用上下文。目前没有淘汰机制，很老的图片描述仍然在送。这是一个已知的、还没解决的问题。

**STT 有延迟。** 语音条要等服务端转写完成才能进上下文，长语音会有明显等待。
