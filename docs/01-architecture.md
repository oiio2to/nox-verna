# 01 · 架构与数据落地

> 服务怎么分、请求怎么走、数据落在哪，以及两个会被质疑的选择：为什么不用数据库，为什么前端是一个 13,000 行的文件。

---

## 拓扑

```
                iPhone PWA (React 19 · 单文件 App.jsx)
                          │  HTTPS + 门禁 cookie
                          ▼
    Nginx ─────────── Node 网关 server.js
                          │  AI 代理 · 媒体处理 · cron · 工具执行 · 用量台账
                          │
      ┌───────────────────┼───────────────────┐
      │                   │                   │
  模型中转层          微服务集群            MCP 服务
  OpenAI 兼容         脉搏花园  :8804       外置记忆库
  Anthropic 原生      共读服务  :18010      VPS 执行
  上游可插拔          眼睑森林 / 骨骼温室    Web 搜索
                      Telegram 桥
```

七个常驻 systemd unit：网关、Telegram 桥、脉搏花园、共读服务、共读 MCP、外置记忆库、嵌入服务。

**网关是唯一的对外入口。** 所有微服务只监听 `127.0.0.1`，不暴露端口。这不只是安全考虑——它意味着微服务之间可以省掉认证，因为能访问到它们的只有本机的网关。

## 请求链路

一次普通聊天请求：

```
前端组装上下文（分层，见 02）
   → POST /api/chat
   → 网关切分 system、挂缓存断点
   → 转发到中转层（SSE 流式）
   → 边流边解析 ⟦TOOL⟧ 标记（见 04）
   → 工具执行 → 结果回填 → 继续流
   → 流结束：记账、写入会话、触发副作用（记忆、脉搏）
```

副作用是在流结束**之后**触发的，不阻塞回复。用户看到完整回复的那一刻，记忆写入和情绪演化还在后台跑。

## 数据落地：JSON 文件 + 原子写

没有数据库。所有状态是文件系统上的 JSON：

```
data/
  chat/s<id>.json      会话
  forest/forest.json   森林
  greenhouse/          温室
  moments.json         朋友圈
  pf_data.json         脉搏状态
  daily-obs.json       每日观察
  media/               媒体文件
```

写入一律走原子替换：

```js
function save(d) {
  fs.mkdirSync(DIR, { recursive: true });
  const t = FILE + ".tmp";
  fs.writeFileSync(t, JSON.stringify(d));
  fs.renameSync(t, FILE);      // rename 在同一文件系统上是原子的
}
```

`rename` 保证任何时刻读到的都是完整的旧版本或完整的新版本，不会读到写了一半的文件。这是用文件当数据库时最容易被忽略、也最要命的一点。

### 为什么不用数据库

在这个规模下（单用户、单机、数据量以 MB 计），JSON 文件的三个性质压倒了数据库的收益：

| | |
|---|---|
| **可读** | 出问题时 `cat` 一下就知道状态是什么，不需要连进 psql 写查询 |
| **可备份** | `tar` 整个目录就是一次完整快照 |
| **可手修** | 数据结构改错了，用 `jq` 或者一段 Python 就能改回来。数据库要写迁移 |

代价也很明确：

- **并发写会丢数据。** 原子写保证不写坏文件，但两个并发写会互相覆盖（后写的赢）。单用户场景下这几乎不发生，多用户就必然出问题。
- **没有事务。** 跨文件的一致性靠代码顺序保证，中途崩溃会留下不一致状态。
- **全量读写。** 每次改一条要读整个文件、改、写回。文件涨到几十 MB 就会明显变慢。

**这是一个明确按规模做的选择。** 如果这个项目要支持第二个用户，第一件事就是换 SQLite。

## 单文件前端

`App.jsx` 13,098 行，没有拆分。

这是有意的，理由只有一个：**一个人维护的项目，全局可 grep 比模块边界更有价值。**

具体收益：

- 所有状态在一个作用域里，跨面板联动不需要在十个文件之间跳
- 「这个状态是在哪里改的」这个问题，一次全文搜索就有答案
- 没有 props 逐层传递，没有为了共享状态引入的 context / store 样板

具体代价：

- 编辑器会卡，语法高亮偶尔失效
- 无法多人并行编辑，合并冲突会是灾难
- 打包体积无法按面板拆分，首屏加载全量 JS
- 新人接手的心理门槛极高

**如果这是团队项目，我不会这么做。** 模块边界的价值在于隔离——多人协作时，隔离比可见性重要。但在单人项目里，隔离带来的主要是查找成本。

编辑方式也因此固定下来：不靠 IDE 重构，靠精确的字符串替换，每次替换前断言匹配数唯一。这个模式在 [11 · 部署与运维](11-deployment.md) 里详细写。

## 微服务的边界怎么划

拆出去的都满足同一个条件：**有独立的状态和独立的生命周期。**

| 服务 | 独立的理由 |
|---|---|
| 脉搏花园 | 有自己的衰减时钟，必须持续运行，不能跟着网关重启就归零 |
| 森林 / 温室 | 有自己的寿命规则和定时清理 |
| 共读 | EPUB 解析是 CPU 密集的，崩了不该拖垮网关 |
| Telegram 桥 | 独立的长连接，重连逻辑与网关无关 |

没拆出去的是媒体处理、cron、工具执行——它们是无状态的，拆出去只增加一层调用，不带来任何隔离收益。
