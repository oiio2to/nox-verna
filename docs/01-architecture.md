# 01 · 架构与数据落地

> 服务怎么分、请求怎么走、数据落在哪，以及两个会被质疑的选择：为什么不用数据库，以及前端为什么从一个 13,000+ 行的单文件演进成了分层结构。

---

## 拓扑

```
                iPhone PWA (React 19 · App.jsx + lib/ + components/)
                          │  HTTPS + 门禁 cookie
                          ▼
    Nginx ─────────── Node 网关 server.js
                          │  AI 代理 · 媒体处理 · cron · 工具执行 · 用量台账
                          │
      ┌───────────────────┼───────────────────┐
      │                   │                   │
  模型中转层          微服务集群            MCP 服务
  OpenAI 兼容         脉搏花园  :8804       外置记忆库
  Anthropic 原生      共读服务  :18010      VPS 执行
  上游可插拔          眼睑森林 / 骨骼温室    Web 搜索
                      Telegram 桥
```

七个常驻 systemd unit：网关、Telegram 桥、脉搏花园、共读服务、共读 MCP、外置记忆库、嵌入服务。

**网关是唯一的对外入口。** 所有微服务只监听 `127.0.0.1`，不暴露端口。这不只是安全考虑——它意味着微服务之间可以省掉认证，因为能访问到它们的只有本机的网关。

## 请求链路

一次普通聊天请求：

```
前端组装上下文（分层，见 02）
   → POST /api/chat
   → 网关切分 system、挂缓存断点
   → 转发到中转层（SSE 流式）
   → 边流边解析 ⟦TOOL⟧ 标记（见 04）
   → 工具执行 → 结果回填 → 继续流
   → 流结束：记账、写入会话、触发副作用（记忆、脉搏）
```

副作用是在流结束**之后**触发的，不阻塞回复。用户看到完整回复的那一刻，记忆写入和情绪演化还在后台跑。

## 数据落地：JSON 文件 + 原子写

没有数据库。所有状态是文件系统上的 JSON：

```
data/
  chat/s<id>.json      会话
  forest/forest.json   森林
  greenhouse/          温室
  moments.json         朋友圈
  pf_data.json         脉搏状态
  daily-obs.json       每日观察
  media/               媒体文件
```

写入一律走原子替换：

```js
function save(d) {
  fs.mkdirSync(DIR, { recursive: true });
  const t = FILE + ".tmp";
  fs.writeFileSync(t, JSON.stringify(d));
  fs.renameSync(t, FILE);      // rename 在同一文件系统上是原子的
}
```

`rename` 保证任何时刻读到的都是完整的旧版本或完整的新版本，不会读到写了一半的文件。这是用文件当数据库时最容易被忽略、也最要命的一点。

### 为什么不用数据库

在这个规模下（单用户、单机、数据量以 MB 计），JSON 文件的三个性质压倒了数据库的收益：

| | |
|---|---|
| **可读** | 出问题时 `cat` 一下就知道状态是什么，不需要连进 psql 写查询 |
| **可备份** | `tar` 整个目录就是一次完整快照 |
| **可手修** | 数据结构改错了，用 `jq` 或者一段 Python 就能改回来。数据库要写迁移 |

代价也很明确：

- **并发写会丢数据。** 原子写保证不写坏文件，但两个并发写会互相覆盖（后写的赢）。单用户场景下这几乎不发生，多用户就必然出问题。
- **没有事务。** 跨文件的一致性靠代码顺序保证，中途崩溃会留下不一致状态。
- **全量读写。** 每次改一条要读整个文件、改、写回。文件涨到几十 MB 就会明显变慢。

**这是一个明确按规模做的选择。** 如果这个项目要支持第二个用户，第一件事就是换 SQLite。

## 前端结构：从单文件到分层，以及为什么

前端曾经是一个 13,570 行的 `App.jsx`。这是有意的，理由只有一个：**一个人维护的项目，全局可 grep 比模块边界更有价值。** 收益是真实的——所有状态在一个作用域里，跨面板联动不用在十个文件间跳；「这个状态在哪改的」一次全文搜索就有答案；没有 props 逐层传递、没有为共享状态引入的样板。

但当它涨到 13,570 行时，天平倒向了另一边。真正压垮它的不是「编辑器卡」这类体感问题，而是一个具体的工程约束：**这个文件已经塞不进一次 LLM 辅助编辑的上下文窗口。** 我大量依赖精确字符串替换来改它（每次替换前断言匹配数唯一，见 [11](11-deployment.md)），而当文件超过某个尺寸，「找到唯一锚点」这件事本身开始变得困难和脆弱——同名变量、相似结构、局部遮蔽都会让 `assert count==1` 失败。可维护性的瓶颈从「人能不能读懂」变成了「工具能不能精确定位」。

于是做了一次系统性拆分，把它降到约 7,100 行，其余约 210 个定义搬进 `src/lib/`（纯逻辑）和 `src/components/`（渲染组件）。方法本身是这个项目里我比较满意的一段工程：

- **依赖闭包分析**：不是凭直觉切，而是对每个候选定义算它的引用闭包（它用到谁、谁用到它），保证搬走一个不会拆断另一处。
- **import 自动生成**：脚本解析 App.jsx 现有的 import 表 + 新模块的导出表，对每个新文件的实际标识符求交集，自动写出该文件需要的 import 行——29 个页面组件的那一批，import 是机器算出来的，一次 build 通过。
- **跨模块可变状态的处理**：有四个模块级 `let`（通话模型覆盖、收线时戳等）被多处读写，直接搬会破坏引用。把它们合并成一个导出的状态对象 `chatSt`，跨模块共享一个可变引用——这是 ES module 的 import 绑定不可重新赋值这一约束下的正确解法。
- **每批 build 验证**：分九批做，每批一次 `npm run build` 绿灯才继续，全程运行时行为零变化（Vite 打包后仍是同一 bundle，拆分只改变「人和工具编辑它的体验」，不改变运行时）。

关键的判断是：**单文件不是错误，拆分也不是「终于正确了」——是约束变了，最优解就变了。** 单人项目、文件能整个读进上下文时，可见性 > 隔离；当文件超过工具的处理边界时，隔离（更小的锚点空间、更便宜的上下文）反过来成了可维护性本身。同一个人在不同约束下会给出不同答案，这不是反复，是对约束的诚实。

如果这是团队项目，我一开始就不会写单文件——多人协作时隔离永远 > 可见性。

## 微服务的边界怎么划

拆出去的都满足同一个条件：**有独立的状态和独立的生命周期。**

| 服务 | 独立的理由 |
|---|---|
| 脉搏花园 | 有自己的衰减时钟，必须持续运行，不能跟着网关重启就归零 |
| 森林 / 温室 | 有自己的寿命规则和定时清理 |
| 共读 | EPUB 解析是 CPU 密集的，崩了不该拖垮网关 |
| Telegram 桥 | 独立的长连接，重连逻辑与网关无关 |

没拆出去的是媒体处理、cron、工具执行——它们是无状态的，拆出去只增加一层调用，不带来任何隔离收益。
