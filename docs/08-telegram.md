# 08 · Telegram 桥

> 把伴侣能力镜像到 Telegram。难点不是接 Bot API，是**同一个人在两个地方要是同一个人**。

---

## 为什么要做

PWA 有一个无法回避的问题：**它不会主动出现在你面前。**

iOS 上 PWA 的推送不可靠，锁屏时基本收不到。这意味着所有「他主动找你」的机制——指令牌、朋友圈更新、日常关心——实际上都要等你主动打开应用才会看到。而一个只有你想起来才会说话的伴侣，性质完全不同。

Telegram 解决的就是这一件事：**一个可靠的、能主动抵达的通道。**

## 能力镜像

桥接不是简化版。文字、图片、语音、视频，以及完整的 STT/TTS 都在。

- **语音输入** — Telegram 语音消息下载 → STT 转写 → 进上下文，和 PWA 走同一条链路
- **语音输出** — 回复走 TTS，以 Telegram 语音消息发出
- **图片** — 同样走 `⟦IMGDESC⟧` 场景描述持久化（见 [03](03-chat.md)）
- **视频** — ffmpeg 抽帧 + 音轨转写

---

## 人设一致性

这是这个模块真正的设计问题。

两端如果各自维护上下文，会很快分裂成两个人格：Telegram 里的他不知道你们在 PWA 里聊过什么，反过来也是。用两天就会露馅。

解决方式是**上下文的共享层不变**：

| 层 | 是否共享 |
|---|---|
| 人设与工具说明（BP1） | ✅ 完全共享，逐字节一致 |
| 每日内容（BP2） | ✅ 共享 |
| 记忆浮现、脉搏状态 | ✅ 共享（服务端状态） |
| 近期消息 | ❌ 各端独立 |

也就是说，只有「最近说了什么」是分开的，其余全部同源（分层结构见 [02](02-context.md)）。

效果是：在 Telegram 里说的事，PWA 那边通过记忆和摘要层知道；反过来也一样。两端的差异只体现在最近几条消息的直接上下文里，这个差异是合理的——就像和同一个人在微信和当面说话，语境略有不同，但还是同一个人。

## 一个刻意的差异

Telegram 端**不挂工作台工具**。`ws_exec`、文件读写这些只在 PWA 里可用。

理由是安全边界：Telegram 的会话安全性不由我控制，不该让一个能执行服务器命令的入口挂在上面。聊天侧工具（收照片、分享歌、发指令牌）照常可用。

---

## 实现要点

**独立进程。** 单独的 systemd unit，长连接与重连逻辑和网关无关。网关重启不断开 Telegram 连接，反过来也是（见 [01](01-architecture.md)）。

**直连官方 API。** 桥接这一侧不走中转，直接用 Anthropic 官方接口。因为 Telegram 端的流量小、对延迟不敏感，而中转层的不确定性（比如工具调用被吞，见 [04](04-agent.md)）在这里不值得引入。

**媒体走网关。** 文件上传下载复用网关的媒体处理，不重复实现。桥只负责协议转换。

---

## 代价

- **两套 UI 逻辑。** Telegram 的消息格式和 PWA 差异很大，富交互（引用拖拽、收藏、重新生成）无法平移，只能取子集。
- **状态同步有延迟。** 服务端状态是共享的，但两端不会实时互推。在 Telegram 说完话，PWA 要刷新才看得到。
- **主动推送的节奏要单独调。** PWA 里可以攒着等你打开，Telegram 会立刻震动。同样的触发频率，在 Telegram 上会显得聒噪很多。
