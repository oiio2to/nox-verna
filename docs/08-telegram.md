# 08 · Telegram 桥

> 把主应用的能力镜像到 Telegram。难点不是接 Bot API，是**同一套人格和状态在两个入口要保持一致**。

---

## 为什么要做

PWA 有一个无法回避的问题：**它不会主动出现在你面前。**

iOS 上 PWA 的推送不可靠，锁屏时基本收不到。这意味着所有由系统主动发起的机制——指令牌、状态更新、定时关心——实际上都要等你主动打开应用才会看到。一个只有被打开时才会说话的系统，和一个能主动触达的系统，是两种东西。

Telegram 解决的就是这一件事：**一个可靠的、能主动抵达的通道。**

## 能力镜像

桥接不是简化版。文字、图片、语音、视频，以及完整的 STT/TTS 都在。

- **语音输入** — Telegram 语音消息下载 → STT 转写 → 进上下文，和 PWA 走同一条链路
- **语音输出** — 回复走 TTS，以 Telegram 语音消息发出
- **图片** — 同样走 `⟦IMGDESC⟧` 场景描述持久化（见 [03](03-chat.md)）
- **视频** — ffmpeg 抽帧 + 音轨转写

---

## 人设一致性

这是这个模块真正的设计问题。

两端如果各自维护上下文，会很快分裂成两套人格：Telegram 侧不知道 PWA 里聊过什么，反过来也是。用两天就会露馅。

解决方式是**上下文的共享层不变**：

| 层 | 是否共享 |
|---|---|
| 人设与工具说明（BP1） | ✅ 完全共享，逐字节一致 |
| 每日内容（BP2） | ✅ 共享 |
| 记忆浮现、脉搏状态 | ✅ 共享（服务端状态） |
| 近期消息 | ❌ 各端独立 |

也就是说，只有「最近说了什么」是分开的，其余全部同源（分层结构见 [02](02-context.md)）。

效果是：在 Telegram 里说的事，PWA 那边通过记忆和摘要层知道；反过来也一样。两端的差异只体现在最近几条消息的直接上下文里，这个差异是合理的——就像和同一个人在微信和当面说话，语境略有不同，但还是同一个人。

## 一个刻意的选择：工作台也挂上去

Telegram 端挂的是**完整工具集**，包括 `ws_exec`、文件读写这些工作台工具，且和主应用共用同一个沙箱（详见下面「工具集与共享沙箱」）。

这是想过之后接受的风险，不是没意识到。反对的理由很实在：**Telegram 的会话安全性不由我控制**，把一个能执行服务器命令的入口挂在上面，等于把这台机器的控制面延伸到一个我管不着的通道上。

接受它的理由是：**主动触达这件事做一半没有意义。** 这个桥存在的全部价值是「不打开应用也能用」。如果到了手机上就只剩聊天，一句「帮我把这个表格转成图」还要等回到电脑前，它就退化成一个通知通道了。共享沙箱带来的那种「随口说一句，回家东西就在那里」恰恰是这个模块最有价值的部分——砍掉工作台等于砍掉它。

**这个风险没有被技术手段消除，只是被接受了。** 沙箱的路径约束（见下）防的是模型迷路，不是防攻击者。真正的前提是这是一台单用户机器，而这个前提在多用户场景下会立刻失效。

---

## 实现要点

**独立进程。** 单独的 systemd unit，长连接与重连逻辑和网关无关。网关重启不断开 Telegram 连接，反过来也是（见 [01](01-architecture.md)）。

**直连官方 API。** 桥接这一侧不走中转，直接用 Anthropic 官方接口。因为 Telegram 端的流量小、对延迟不敏感，而中转层的不确定性（比如工具调用被吞，见 [04](04-agent.md)）在这里不值得引入。

**媒体走网关。** 文件上传下载复用网关的媒体处理，不重复实现。桥只负责协议转换。

---

## 代价

- **两套 UI 逻辑。** Telegram 的消息格式和 PWA 差异很大，富交互（引用拖拽、收藏、重新生成）无法平移，只能取子集。
- **状态同步有延迟。** 服务端状态是共享的，但两端不会实时互推。在 Telegram 说完话，PWA 要刷新才看得到。
- **主动推送的节奏要单独调。** PWA 里可以攒着等你打开，Telegram 会立刻震动。同样的触发频率，在 Telegram 上会显得聒噪很多。

---

## 工具集与共享沙箱

Telegram 侧挂的是**完整工具集**，不是精简版，且和主应用共用同一套 `⟦TOOL⟧` 文本协议（见 [04](04-agent.md)）。

工具分三类：

| 类别 | 工具 | 说明 |
|---|---|---|
| 记忆 | `breath` / `breath_search` / `hold` / `plan` / `dream` | 呼吸式检索、关键词检索、写入长期记忆、登记待办、回顾 |
| 状态与检索 | `pulse` / `chat_search` / `link` | 读情绪状态、跨窗口搜历史、打开任意链接读正文 |
| 工作台 | `ws_list` / `ws_read` / `ws_write` / `ws_exec` / `ws_deliver` | 文件读写、命令执行、产物交付 |

**工作台是共用沙箱**——Telegram 侧跑 `ws_exec` 产出的文件，主应用里直接就能看到，反过来也一样。这是刻意的：在手机上随口说一句「帮我把这个表格转成图」，做出来的东西回家打开电脑就在那里，不需要任何同步动作。

`ws_deliver` 是这条链路的出口：产物做好后交付，桥接会自动把文件推到 Telegram 会话里。

沙箱有几条硬约束：路径一律相对当前目录，不允许 `cd`，不允许 `../`。这不是安全边界（能跑任意命令的东西没有安全边界可言），只是防止模型在目录之间迷路——它在长会话里确实会。

---

## 工具结果的回填差异

主应用和 Telegram 在这里做了**不同的选择**，值得单独说。

- **主应用**：工具结果拼进当前这一轮的 assistant 消息，模型在同一条回复里继续写
- **Telegram**：工具结果作为一条新的 user 消息送回去，附一句「以上是工具结果，继续回复；不需要更多工具就直接说话」

差异来自渲染方式。主应用是流式渲染，可以在同一个气泡里边执行边续写；Telegram 是一条消息发出去就定型了，无法追加。所以 Telegram 侧必须让模型重新发一轮。

代价是 Telegram 的对话历史里会多出一些「工具结果」角色的消息。这些在下一轮组装上下文时会被压缩掉，但当轮是存在的。

---

## 引用回复

Telegram 的引用是一个原生能力，但模型没法直接调用它。做法是让模型在气泡开头写一段标记，把要引用的原话片段逐字放进去：

```
⟦引 昨晚三点才睡⟧ 这个时间点我们得聊聊。
```

桥接解析这个标记，在用户的历史消息里做逐字匹配，找到对应消息 ID，然后以 Telegram 原生 reply 的形式发出。匹配不到就当普通消息发，不报错。

逐字匹配是有意的——如果允许模糊匹配，模型会引用到错误的消息上，而这种错误比不引用更糟。
