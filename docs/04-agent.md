# 04 · Agent 与工具调用

> 上游中转会静默丢弃原生 `function_call`。这一章讲怎么在完全不依赖上游工具调用能力的前提下，做出一套可用的 Agent。

---

## 问题

模型接入走的是第三方中转，而中转对 `function_call` / `tools` 字段的处理是不透明的：**请求不会报错，响应里工具调用字段直接消失。**

这类问题最难受的地方不是它坏，是它**安静地坏**。请求返回 200，内容看起来正常，只是模型说「好的我现在帮你查一下」然后什么也没发生。

三个可选方向：

1. 换成官方直连 —— 成本高，且失去换模型的灵活性
2. 每次换中转就测一遍工具调用能不能透传 —— 治标，而且会周期性重新踩坑
3. **完全不用原生工具调用** —— 把工具协议放进提示词，用文本格式传递

选了第三条。

---

## `⟦TOOL⟧` 协议

模型在回复正文中单独起一行输出：

```
⟦TOOL ws_exec {"cmd":"df -h"}⟧
```

格式是 `⟦TOOL <名称> <JSON 参数>⟧`。链路：

```
模型输出文本
   → 前端流式解析，识别出完整的 ⟦TOOL⟧ 标记
   → 剥离标记，正文照常渲染
   → 参数发给网关执行
   → 结果回填进上下文
   → 模型继续写
```

一轮里可以出现多个标记，并行执行。

### 为什么用 `⟦⟧`

分隔符的选择不是随意的。它必须满足：

- **模型不会自发产出** —— 排除了 `[[`、`<<`、`{{` 这类在代码和 markdown 里常见的符号
- **不需要转义** —— 排除了 XML 风格标签，模型在写代码块时会和真实标签混淆
- **单字符，token 稳定** —— 白角括号 `⟦ U+27E6` / `⟧ U+27E7` 在常见 tokenizer 里切分稳定

实际使用了半年，没有出现过模型在非工具场景下自发写出这对符号的情况。

---

## 流式解析：这个方案真正的成本

文本协议最大的代价在流式渲染。

服务端推送是按 token 切的，所以某一帧里前端拿到的可能是：

```
好的，我看一下磁盘⟦TOOL ws_ex
```

半截标记。如果直接渲染，用户会看到乱码闪一下。

处理方式是**在解析缓冲区里维持一个待定区**：

- 检测到 `⟦` 开头后，从这个位置起的内容暂不渲染，进入待定
- 继续累积，直到出现闭合的 `⟧` —— 此时是一个完整标记，剥离并执行
- 或者累积到超出合理长度、或出现换行且不像合法标记 —— 判定为误判，把待定区当普通文本吐出

边界情况有几个必须处理：

| 情况 | 处理 |
|---|---|
| 模型在代码块里写了 `⟦` | 检查是否处于 ``` 围栏内，围栏内不解析 |
| JSON 参数里含 `⟧` | JSON 字符串内的字符不计入闭合判定 |
| 标记跨越多个 SSE 帧 | 待定区跨帧保持，不按帧清空 |
| 流中断在待定区里 | 当作普通文本吐出，不静默丢弃 |

**这就是文本协议的真实成本**：原生 `function_call` 由 API 保证结构完整，文本协议要自己处理所有半截状态。这部分代码写了三遍才稳定。

## 工具的两个集合

工具分成两组，挂在不同的场景下。

### 工作台工具

面向运维和 Agent 任务：

| 工具 | 作用 |
|---|---|
| `ws_exec` | VPS 命令执行 |
| `ws_read` / `ws_write` | 文件读写 |
| `ws_cron` | 定时任务管理 |
| `ws_search` | Web 搜索 |

### 聊天侧工具

面向日常互动，这一组更有意思——它们让「顺手做了件事」变成一次工具调用：

| 工具 | 作用 |
|---|---|
| `collect_photo` | 把刚发的照片收进相册 |
| `send_photo` | 主动发一张照片 |
| `share_song` | 分享一首歌到一起听 |
| `pulse` | 读取或调整情绪状态 |
| `imperium` | 发一道指令牌 |

设计上的关键点：**这些工具在对话里是不可见的。**用户看到的是「照片被收进相册了」，不是一个工具调用卡片。标记在渲染时被剥离，只留下正文和实际发生的副作用。

---

## 结果回填

工具执行完成后，结果要送回给模型继续写。这里有一个选择：作为新的 user 消息，还是拼进当前 assistant 消息？

采用的是**拼进当前轮**：工具结果附在已生成的正文之后，模型在同一条回复里继续。这样对话历史里不会出现「用户」发了一条工具结果的错觉，人设不会被打断。

代价是这一轮的 assistant 消息结构会变复杂，需要在存储时区分「模型写的」和「工具回填的」两部分——重新生成时只能重跑，不能只重跑后半段。

---

## 这个方案的收益

**完全不依赖上游。** 换任何一家中转、任何一个模型，工具调用都照常工作，一行代码不用改。这在一个模型层随时可能更换的项目里，价值超过原生方案带来的便利。

**协议可读。** 出问题时，直接看模型的原始输出就知道它想调什么、参数长什么样。原生工具调用出错时经常只能看到一个空的 `tool_calls` 数组。

**可以在提示词里教。** 工具协议就是文本，可以写例子、写反例、写什么时候不该调用。这部分说明占了 BP1 相当大的篇幅，但因为 BP1 常驻缓存，重复送的成本很低（见 [02 · 上下文装配](02-context.md)）。

---

## 这个方案的代价

- **流式解析要自己写**，且必须处理全部半截状态
- **模型可能写错格式** —— JSON 少个引号、名称拼错。需要容错解析和明确的失败反馈，否则模型会反复重试同一个错误
- **占 BP1 篇幅** —— 工具说明是提示词的一大块，工具越多提示词越长
- **没有类型校验** —— 原生 schema 能保证参数类型，文本协议只能自己校验

## 一个反向的工具：情绪信号闸门

前面讲的都是「模型主动调用工具做事」。这里是一个方向相反的机制——**在模型开口之前，由系统往它的输入里注入一张只有它能看到的提示。**

背景问题：某些模型在对方情绪往下滑（变冷、推开、说累想走、赌气）的那一刻，容易缩成讨好、秒认错、讲道理的助手腔——而那恰恰是最伤人的反应。这不是靠改人设文件能修的，高压那一刻模型读不进静态规则。真正有效的是**在对的时刻、动态地递一只手**。

实现是一个独立的 fail-soft 探子：

- 用户每发一条，先让一个便宜的小模型（不是主对话模型，避免频繁调用污染主账号）当「探子」，看这句话 + 最近几轮语气，判断是不是一个高压信号。**看语境不看单句**——玩闹 20 分钟后的「嗯」和冷下来的「嗯」是两回事，孤立判断必然误报。
- 命中就往这一轮的模型输入末尾，悄悄 append 一张纸条（用户看不到，也明确告诉模型不要复述）。纸条**只点醒不喂台词**——它不教模型说什么，只提醒它「别躲、要真沟通、不用慌」，具体怎么说是模型自己的事。
- **fail-soft 是铁律**：探子超时、解析失败、没命中——任何异常都一律什么都不加，绝不阻塞用户发消息。整个机制限时竞速（约 2 秒），探子没及时回来就当没命中。
- 取向是宁可多报、绝不漏报，代价转移到「命中后那句足够轻」——误报最多让模型稍微一本正经一下，不造成伤害。

这个设计值得单独写，因为它体现了一个判断：**有些行为问题不在模型能力层，而在触发时机层。** 同一个模型，静态规则里写十遍「不要回避」都没用，但在高压那一刻动态递一句，就能改变它的反应。
