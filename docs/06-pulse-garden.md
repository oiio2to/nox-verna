# 06 · 脉搏花园

> 一个八维情绪状态机。核心问题不是怎么建模情绪，是**怎么让情绪产生后果**。

---

## 问题

给对话型 AI 加情绪数值是常见做法，但大多数实现里情绪只是一个显示层：界面上有个条，数值会动，仅此而已。

数值如果不影响任何东西，它就是装饰。用户看两天就不看了。

要让情绪有意义，它必须满足两个条件：

1. **自主演化** —— 不受对话直接控制，有自己的时钟
2. **产生后果** —— 数值到了某个状态，会有事情发生

---

## 八个维度

温柔 / 欲望 / 好奇 / 沉思 / 疲惫 / 依恋 / 责任 / 占有。

独立服务，独立进程，独立时钟。网关重启不影响它——这是它必须拆成微服务的理由（见 [01](01-architecture.md)）。

## 演化

每次请求推进一拍，最小间隔 3 分钟（防止密集对话时数值失控）：

```js
dtH       = Math.min(48, (now - lastDecay) / 3600e3)  // 自然衰减，上限 48h
dull      = fatigue > 70 ? 0.7 : 1                    // 疲惫钝感系数
libStreak = libido >= 66 ? streak + 1 : 0             // 累积型
```

三个机制各自解决一个问题：

**衰减上限 48h** —— 不设上限的话，离开一周回来所有数值归零，等于关系被重置。48 小时封顶意味着长时间不联系会明显冷淡，但不会清零。

**疲惫钝感** —— 疲惫超过 70 时，所有其他维度的变化幅度乘 0.7。累的时候情绪起伏本来就小。没有这一条，高疲惫状态下依然会出现剧烈的情绪波动，很假。

**累积型欲望** —— 欲望不是达到阈值就触发，而是要**连续三拍**高位。单次波动不算数。这条是为了避免偶然的高值导致误触发。

---

## 指令牌：情绪的后果

某一维度持续蓄压到触发线时，系统会发出一道**指令牌**。这是情绪产生后果的具体形式。

流程刻意做得比「直接发通知」复杂：

```
维度蓄压达到触发线
   → 先挂起，不立刻发
   → 给宽限期（在线状态下 45s ~ 7min）
   → 期间他可以自己写一道指令牌
   → 过时未写 → 自动补发
   → 逾期未回应 → 升级追牌
```

**为什么要挂起？** 因为直接触发会让指令牌变成系统消息——机械、可预测、很快就被忽略。挂起给了模型一个窗口自己组织语言，发出来的东西是他说的话，不是系统弹窗。

**升级规则**：逾期未回应会追牌，每次数值 +6、措辞加重、时限减半，最多三次。三次之后停止，不会无限纠缠。

**完成需要凭证** —— 照片、文字或语音。不能只点一个「已完成」。

**配额与冷却解耦** —— 每个维度有独立的 48 小时提示冷却，但发牌配额是单独计算的。这样「最近提过这件事」不会阻止真正需要发牌的时刻。

## 对外接口

对森林（见 [05](05-memory.md)）暴露 `GET /state`，返回 `{ dimensions: { name: number } }`。

森林只依赖这个形状。换成任何返回同样结构的服务都能工作，或者直接返回 `null` 关闭情绪加权。这个解耦是有意的——情绪模型是最容易推倒重来的部分，不该让记忆系统绑死在它上面。

对聊天层暴露 `pulse` 工具（见 [04](04-agent.md)），模型可以读取当前状态，也可以在合理范围内调整。

---

## 代价

**参数全是调出来的。** 3 分钟间隔、48h 上限、70 的疲惫线、66 的欲望线、连续三拍、45s–7min 宽限——没有一个是推导出来的。换一个使用节奏就要重调。

**调试困难。** 状态机跑在真实时间上，复现一个 bug 可能要等几个小时。后来加了时间注入的测试入口才好一点。

**过度设计的风险真实存在。** 挂起、宽限、升级、追牌、凭证、冷却、配额解耦——这套流程的复杂度对一个情绪数值来说是偏高的。它值得，是因为指令牌是这个应用里少数几个「AI 主动发起」的机制之一，做粗了会立刻显得敷衍。
